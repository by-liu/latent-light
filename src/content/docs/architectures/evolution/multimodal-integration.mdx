A language model cannot read pixels merely because an image is attached.
A visual interface must turn image evidence into features the language system
can consume. Its design determines **what survives**, **how much enters**, and
**where the decoder can use it**.[^blip][^llava][^qwen]

BLIP-2 uses learned queries in a Q-Former to read image encoder features.
In its generative pretraining stage, projected query outputs become soft
visual prompts for a frozen language model. The image encoder is also
frozen.[^blip]

The original LLaVA instead projects CLIP image features directly into the
language embedding space. It first trains that projection with both
backbones frozen, then trains the projection and language model for
instruction following while keeping the image encoder frozen. These labels
refer to the original design, not every later LLaVA variant.[^llava]

Qwen3-VL merges visual features for the decoder input and also uses
intermediate encoder features at early decoder depths. Its
[model study](/architectures/models/qwen3-vl/) explains those additional
DeepStack connections.[^qwen]

The key difference is not simply connector size: a query bottleneck, direct
projection, and input plus depth integration give evidence different routes.

## Count the evidence before estimating cost

For an image of height `H` and width `W`, split into square patches of side
`P`, the basic patch count is:[^vit]

<MathExpression display number="1" tex="N_{\mathrm{patch}}=\frac{H}{P}\frac{W}{P}" />

This assumes both dimensions are divisible by `P`, with no padding or crops.
Doubling both dimensions gives four times as many patches, not necessarily
four times the total latency. These are geometry calculations, not a
checkpoint's final token count.

Processing can resize, crop, sample video frames, merge features, and add
special tokens. Count **encoder patches** separately from **visual tokens
passed to the language model**. BLIP-2's fixed set of query outputs illustrates
why those counts need not match.[^blip]

## Architecture and training belong together

| Question | Why it matters |
| --- | --- |
| Which backbone is frozen? | A connector may need to align features to a fixed language representation |
| What supervision is used? | Caption alignment and instruction following teach different interfaces |
| What is compressed? | A shorter visual sequence may omit fine details needed by the task |
| Where do features enter? | Input embeddings and additional depth connections are different designs |

This is a local comparison framework, not a claim that one interface always
preserves more information. Its usefulness must be tested.

## Test whether the answer uses the image

Proposed evaluations should compare correct, missing, and contradictory visual
evidence. Include small text, charts, spatial relations, and questions that
cannot be answered from text alone. Control resolution, visual budget, and
training conditions before attributing gains to the connector.

The cited models are examples of design choices, not recommendations or
guarantees of visual grounding. Selected mechanisms checked October 5, 2026.
