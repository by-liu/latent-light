Architectures evolve because useful capabilities meet practical limits.
Rather than follow release names, ask what changes in the computation,
what problem that change addresses, and what it costs.

This is an editorial reading map, not an exhaustive taxonomy or a ladder from
obsolete to superior designs. Several choices can coexist in one model.

## Read a change in five steps

1. Name the problem and the baseline.
2. Locate the operation or stored representation that changes.
3. Identify what stays the same.
4. Compare quality, computation, memory, and implementation cost.
5. Check the experiment's conditions before generalizing its result.

For example, FlashAttention changes how attention is executed; GQA changes
how heads share keys and values; causal linear attention changes the memory
operator.[^flash][^gqa][^linear] Calling all three “efficient attention” hides the distinction.
The [attention page](/architectures/evolution/attention-and-memory/) explains
each mechanism and its source evidence.

## Connect mechanisms to models

Use [GPT-2](/architectures/models/gpt-2/) to trace a language decoder and
[Qwen3-VL](/architectures/models/qwen3-vl/) to examine a visual interface
that also reaches inside the decoder. Neither is presented as the endpoint
of architectural progress.

The collection grows through deliberate research and review. A page's
`lastUpdated` date records an edit; its evidence note records the sources
checked. Neither implies automatic monitoring of every new publication.
