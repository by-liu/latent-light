Edge AI brings intelligence close to where it is used: a phone, a laptop,
a camera, an embedded system or a small sensor. The challenge is not simply
to make a large model smaller. It is to deliver a useful capability within
the device's memory, compute, responsiveness and energy limits.

[Figure 1](#figure-1) maps the collection: capable models, efficient execution
and dependable systems, all shaped by shared device budgets.

This is broader than a smaller language model. It includes speech, streaming
perception and specialist models. Local execution is a design option, not a
rule that every task must stay on the device.

The three territories are connected decisions, not fixed pipeline stages.
An architecture or training change can alter execution cost; the product's
deadline or sensory inputs can change which model is useful. The image's
shrinking blocks represent cheaper numerical storage, not removed layers;
its traces are schematic, not measured performance.

## From the task to the device

A model that fits on disk can still fail in memory. An accelerated graph
can lose time crossing processor boundaries. Mobile deployment guidance
makes both constraints explicit; MCUNet demonstrates designing a model and
runtime together.[^ort][^mcunet]

## How to read the evidence

This is a learning map, not a device leaderboard. Chapters distinguish
reported findings, mechanism explanations and our own illustrative
calculations. The original collection was reviewed on October 12, 2026;
focused companions give their own review dates. Mutable runtime documentation
should be checked again for the versions you deploy.
No device benchmark was run for this collection.

The practical goal is to find a **feasible design that meets the task**.
When a reported gain matters, carry its model, precision, input length,
backend and measurement conditions with it.
