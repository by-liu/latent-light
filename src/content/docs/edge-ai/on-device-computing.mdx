If you know how to train or serve a model on cloud GPUs, the mathematics of
device inference will feel familiar. The unfamiliar part is **where the work
runs, how its data moves, and what else shares the machine**.

A phone is not a smaller GPU server. Its CPU, GPU, neural accelerator, camera
and audio engines form a coordinated system. A camera, television or robot
has a different balance again. The useful question is not “Which chip has the
most TOPS?” but **“Which complete device can execute my workload, with the
required quality, responsiveness and sustained power?”**[^ort-mobile][^thermal]

This page builds that mental model, then introduces current flagship families
and representative specialist platforms. It focuses on inference, not chip
design or a buying recommendation. The hardware and software sources were
checked **October 12, 2026**. Vendor specifications are not our measurements;
announcements and availability claims are identified separately.

## From a cloud GPU to a device system

Think in three layers: **execution engines, memory topology and the product
envelope**. Changing only the first can leave the real bottleneck untouched.
[Figure 1](#figure-1) compares three useful memory arrangements.

A conventional discrete GPU server has CPU memory and a separate GPU memory
pool. You stage inputs and weights onto the GPU, then try to keep useful work
there. An integrated device can let processors access a shared physical pool.
MLX, for example, exposes shared arrays to the CPU and GPU on Apple silicon.
This can avoid copying the same tensor between separate memory pools, but it
does not remove execution dependencies.[^cuda-memory][^mlx]

These are **topologies, not location rules**. A desktop RTX card also has
dedicated memory; DGX Spark is a local machine with coherent shared memory.
Cloud systems can use coherent CPU and GPU designs as well. “Unified memory”
must be read in the context of the hardware and runtime, not treated as a
promise of unlimited fast GPU memory.[^rtx][^spark][^cuda-memory]

<ComparisonTable id="cloud-device-contract" title="What changes when the application moves onto a device" label="Cloud GPU service versus on device application" itemLabel="dimensions">

| Dimension | A cloud GPU service often optimizes | A device application must also consider |
| --- | --- | --- |
| Workload | Many requests, batching and service utilization | One interactive user, camera streams or several competing features; batching may add unacceptable delay |
| Memory | GPU capacity, memory traffic and multi-GPU communication | The model shares a budget with the OS, app, display and sensor buffers; allocation limits can be below installed RAM |
| Execution | A selected server architecture and software image | CPU, GPU and NPU placement, driver versions, supported operators and multiple device generations |
| Power and cooling | Facility and accelerator limits under managed cooling | Battery, enclosure, surface temperature and sustained use; a plugged-in TV still has thermal limits |
| Inputs | Requests that have already crossed a network boundary | Capture, timestamps, ISP/DSP processing and evidence that can become stale while inference runs |
| Reliability | Service recovery and fleet observability | Model downloads, offline readiness, interruption, app lifecycle and local fallback |

</ComparisonTable>

This is a design comparison, not a claim that cloud systems lack latency or
power constraints. It combines mobile runtime, thermal and sensor platform
contracts.[^ort-mobile][^thermal][^stm32][^nxp] See
[Production and product design](/edge-ai/production-product-design/) for the
application lifecycle.

## Inside a heterogeneous chip

A **system on chip**, or SoC, integrates several functions behind one system
interface. It need not be one silicon die: Apple's M5 Pro and M5 Max combine
two dies in one SoC. A **system on module**, or SoM, adds a board-level package
around a processor, memory and other required components. A developer kit
adds a carrier board, connectors and a usable development environment.
Jetson distinguishes production modules from developer kits.[^m5][^orin]

[Figure 2](#figure-2) shows the roles, not the floorplan of a particular vendor.
An actual device can omit, combine or duplicate these engines.

**NPU** means neural processing unit, **DSP** digital signal processor, and
**ISP** image signal processor. The names identify intended roles, not a
uniform hardware design or a guarantee of application access.

| Engine | A useful mental model | Typical contribution | Important boundary |
| --- | --- | --- | --- |
| CPU | Flexible control plus vector instructions | Tokenization, parsing, scheduling, tools, small kernels and unsupported operations | Not only a fallback; vector or matrix instructions can make some AI work efficient |
| GPU | Programmable parallel throughput | Large matrix work, image models, decoding kernels, graphics and some local training | Many GPUs already contain specialized matrix units; compute competes with graphics and memory traffic |

| Sensor hub / microcontroller | A small ongoing control domain | Capture timing, low duty-cycle signals, triggers and control | A trigger can wake heavier processing; safety and timing require their own system design |

The role map is a synthesis, not a mandatory allocation rule. CUDA describes
the CPU/GPU control-versus-throughput distinction; Arm's Ethos range and the
QNN and OpenVINO interfaces show why NPU execution is a separate software
contract. NXP, ST and Qualcomm expose concrete sensor and control domains.
An engine's existence does not prove that your app can program it directly.[^cuda][^arm-npu][^qnn][^openvino][^nxp][^stm32][^snapdragon]

### GPU matrix units are not the same thing as a separate NPU

Modern GPU arithmetic includes specialized matrix hardware. RTX 5090 has
Tensor Cores; M5 GPUs have Neural Accelerators in their GPU cores; Snapdragon
8 Elite Extreme Gen 6 lists Adreno matrix cores alongside its Hexagon NPU.
The word “neural” therefore does not identify a single execution path.[^rtx][^m5][^snapdragon]

On a Mac, **MLX's shared-array CPU/GPU path is not an Apple Neural Engine
backend**. Core ML separately lets an application allow CPU, GPU and Neural
Engine combinations, with the OS selecting among permitted compute units.
Allowing an engine is not a guarantee that the entire model runs on it.[^mlx][^coreml]

## Memory often decides the feasible model

Separate four quantities: **stored weights, working capacity, memory bandwidth
and data layout**. A checkpoint can fit on disk but fail in working memory.
Shared DRAM can improve capacity flexibility while remaining a bandwidth
bottleneck. Small on-chip caches or SRAM are faster working spaces, not
permission to keep the whole model there.[^ort-mobile][^mlx][^stm32]

HBM, GDDR and LPDDR are DRAM families, not model formats. In the examples
here, HBM serves the cloud accelerator, GDDR the discrete graphics card,
and LPDDR integrated PC and embedded platforms. The memory name alone does
not establish capacity or attainable bandwidth.[^h200][^rtx][^x2][^thor]

For a bus making <MathExpression tex="r" /> transfers per second across
<MathExpression tex="w" /> data bits, the theoretical payload bandwidth is:

<MathExpression display number="1" tex="\beta_{\mathrm{peak}}=\frac{r w}{8}\quad\mathrm{bytes/s}" />

This is bus-width arithmetic, not attained application bandwidth. Snapdragon
X2 Elite's published 9,523 MT/s and 128-bit memory interface gives
approximately **152.4 GB/s**, consistent with its rounded **152 GB/s**
specification. Different SKUs also list 192-bit interfaces and 228 GB/s.
Do not convert an MT/s rating as if it were a separate clock to double again.[^x2]

To see why capacity and bandwidth are different, compare Apple's published
M5 Max maximum of **128 GB and 614 GB/s** with H200's **141 GB and 4.8 TB/s**.
Their capacities are in the same broad range, but their memory paths and
system envelopes are not. H200 is a cloud reference example here, not a claim
that it is the newest data-center chip.[^m5][^h200]

For a hypothetical decoder that reads **4 GB** of packed weights per accepted
token at an effective **100 GB/s**, the traffic bound is:

<MathExpression display number="2" tex="t_{\mathrm{weights}}\geq\frac{4\times10^9}{100\times10^9}=0.04\ \mathrm{s}" />

That is **40 ms**, or at most **25 tokens/s** from weight traffic alone under
this one-sweep, one-token-per-step premise. Cache reads, arithmetic, unpacking
and synchronization remain; overlap, batching and multi-token verification
can change the premise. This is our illustrative calculation, not a chip
benchmark. [Foundations](/edge-ai/foundations/#compute-and-bandwidth-are-different-bottlenecks)
and [Efficient inference](/edge-ai/efficient-inference/) develop these bounds.

### Shared memory does not mean zero boundary cost

Sharing physical DRAM can avoid a copy between separate pools. It does not
guarantee that CPU, GPU and NPU can consume the same buffer format without
conversion, synchronization or a driver-managed copy. Google's LiteRT guide
warns that split GPU/CPU graphs can be slower than CPU-only execution because
of synchronization. Keep the tensor on a compatible path, not just on the
same motherboard.[^mlx][^litert]

The installed RAM is also not an app reservation. Retain space for the KV
cache, activations, compiler/runtime workspace, OS and sensor buffers.
Budget the allocations that coexist. See
[peak memory lifetimes](/edge-ai/foundations/#peak-memory-follows-lifetimes).

## Read performance labels without being misled

**TOPS** means trillions of operations per second; **TFLOPS** counts floating
point operations. GOPS uses billions rather than trillions: 600 GOPS is
0.6 TOPS only under the same operation-counting convention. None of these
labels tells you how many useful tasks finish. Read the
precision, sparsity rule, included engines and power mode beside the number.

The ambiguity is concrete: Hailo's same 10H module lists **40 TOPS at INT4**
and **20 TOPS at INT8**. NVIDIA lists T5000's **2,070 TFLOPS as sparse FP4**,
while Orin Nano's **67 TOPS is sparse INT8**. Those figures are not one
comparable performance axis.[^hailo][^thor][^orin]

<ComparisonTable id="spec-reading" title="Six questions for any chip specification" label="How to interpret AI chip performance specifications" itemLabel="checks">

| Label | What to ask | What it does not establish |
| --- | --- | --- |
| Precision | INT4, INT8, FP16, BF16 or FP4? What is the accumulation format? | That a four-bit checkpoint uses every operation at four bits |
| Sparsity | Dense work or an assumed supported sparsity pattern? | That ordinary dense weights reach the advertised sparse rate |
| Engine scope | NPU alone, GPU alone or a sum across the platform? | That one indivisible graph can exploit the sum simultaneously |
| Shape | Which batch, sequence length, convolution or matrix dimensions? | That peak utilization holds for batch-one decoding or small kernels |
| Memory | Capacity, theoretical bandwidth and actual tensor traffic? | That stored size predicts runtime peak or effective bandwidth |
| Power | Chip TDP, module mode, board power, supply rating or measured energy? | That these are interchangeable or equal to whole-product battery drain |

</ComparisonTable>

This is an editorial inspection checklist grounded in the variant and scope
differences above. DGX Spark makes the last distinction especially clear:
**140 W GB10 thermal design power (TDP)** and a **240 W power supply** are different specifications,
not two measurements of its workload energy.[^spark]

Compression must match the accelerator's actual arithmetic and packing.
An INT4 weight file may use floating point activations or be expanded by a
backend. Quantization, supported kernels and retained accuracy must be
verified together. Continue with
[Quantization and compression](/edge-ai/quantization-compression/).

## The runtime is part of the hardware contract

A PyTorch model is not automatically a program for every device engine.
Export, quantization, graph lowering and backend-specific compilation decide
which operations can execute. The fallback graph, temporary buffers and
initialization work remain part of the application.[^qnn][^openvino][^ryzen-software]

<ComparisonTable id="hardware-software-paths" title="A map of developer entry points" label="Common device hardware and software execution paths" itemLabel="paths">

| --- | --- | --- |
| Apple GPU versus Neural Engine | MLX/Metal for CPU/GPU work; Core ML for supported compute-unit combinations | Model conversion and actual compute placement; MLX does not silently become a Neural Engine backend.[^mlx][^coreml] |

## Match the device to the complete workload

Three examples make the design consequences concrete. They are proposed
allocations, not measured implementations.

**A local PC document assistant.** Capacity and effective bandwidth decide
whether the model, visual input and cache coexist comfortably. A GPU path may
be easier to experiment with; an NPU path may suit a supported production
model. Test prefill and decoding separately rather than choose by NPU TOPS.

**Glasses or a camera.** Preserve capture timestamps and use inexpensive
continuous processing to decide when a larger model should run. Include the
ISP/DSP, view selection, radio and response delivery in the energy budget.
A phone companion or permitted cloud route may be part of the design; local
capture is not proof of local reasoning. Qualcomm's on-glass demo establishes
one small-model configuration, not a universal architecture.[^ar-demo]

**A robot.** Perception, language reasoning, planning and fast control have
different deadlines. NXP's separate application and microcontroller domains
illustrate why these can be separated. Our design recommendation is to retain
a bounded control and recovery path rather than depend on an unconstrained
language response meeting every deadline. A chip's safety-related feature
does not certify the complete robot.[^nxp]

Keep the device model, RAM configuration, firmware, OS, driver, runtime,
checkpoint, quantization, input shapes, output lengths and power mode in the
test record. Measure correctness, first useful result, completion, peak
allocation, sustained temperature and energy for the same workload. TDP and
a supply rating cannot replace measured joules per useful task.

The most valuable research question is often **what representation and
execution path preserve the capability within this device's envelope?**
