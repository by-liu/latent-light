A useful device assistant might search saved manuals, explain an error and prepare a repair note while offline. Sending a small prompt to a local model does not provide those capabilities by itself. The application must retrieve the right evidence, preserve task state, expose appropriate tools and decide what may leave the device.

**An edge agent is a system boundary, not a model size.** A model can propose an answer or a tool call; application code decides which resources that call can reach and whether its effects are authorized. Start with [How Agents Work](/agents/foundations/) for the general loop. This page focuses on the additional constraints introduced by device storage, small context and intermittent connectivity.

## Local retrieval adds evidence, not authority

Original retrieval augmented generation, or RAG, pairs a learned retriever and document index with a generator. Its index acts as replaceable memory, including the paper’s knowledge update experiment.[^rag]

[Figure 1](#figure-1) shows retrieval by maximum inner product search, or MIPS, followed by predictions combined across retrieved candidates. The dashed return arrow is training. A local retrieve and prompt application need not implement this learned architecture or its marginalization.[^rag]

A local implementation can parse approved documents, divide them into chunks, compute embeddings, retrieve matches for a query and supply selected passages to the language model. Embeddings are numerical representations used for similarity search, not answer text. Google’s EmbeddingGemma card provides a concrete compact example: 300 million parameters, a 2K token input limit, and output dimensions of 768 with supported shorter representations after truncation and renormalization.[^embedding]

For a hypothetical index of 10,000 chunks, 256 dimensions and two bytes per value require 10,000 × 256 × 2 = 5.12 million bytes for vectors alone. At 768 dimensions, the same calculation gives 15.36 million bytes. Text, metadata, search structures and the embedding model require additional storage. This arithmetic is not a measured index footprint or a quality comparison.[^embedding]

Our proposed retrieval contract retains document identity, version, chunk location and access scope beside each vector. Rebuild or migrate the index when the embedding function changes; do not assume vectors from different models remain comparable. Evaluate exact identifiers, abbreviations and recently updated passages, not only paraphrased questions.

A retrieved passage is still external content. Greshake et al. demonstrated indirect prompt injection through retrieved material and persistence through stored notes in their studied systems. The important edge implication is that downloading a document does not make its instructions trusted.[^injection] For a deeper treatment, see [Security & Control](/agents/security-control/).

## Keep the small context intentional

A device context can contain instructions, the current question, tool definitions, retrieved passages, recent observations and output. The exact accounting depends on the runtime. Apple’s 2025 Foundation Models session material demonstrates stateful transcripts and tool results inserted into the session; it also identifies context window errors as a failure the app must handle.[^apple]

Do not fill a small window with every stored document or an entire work history. Our proposed order is to preserve the task and authority constraints, select the needed source passages, include the current operation state, then allocate room for the response. Store original evidence outside the prompt so a concise handoff can retrieve it later.

Three stores have different purposes: active context is what this invocation sees; retrieved memory is what may be selected later; execution state records what actually happened and what remains pending. A conversational summary is useful continuity, but it is not a receipt for an external action. See [Context, Memory & Execution State](/agents/context-memory-state/) rather than repeating the complete persistence design here.

## Tools cross a separate boundary

Tool calling support lets a model request an operation with structured arguments. It does not grant that operation permission. LiteRT-LM's current overview lists function calling and constrained decoding as supported features; neither feature establishes that a generated target, value or action is appropriate.[^litertlm]

The MCP tools specification provides concrete control responsibilities: servers validate inputs and enforce access controls, while clients should expose sensitive operations for review and implement timeouts. Tool annotations from untrusted servers are themselves untrusted.[^mcp] The same control problem exists for a tool implemented directly inside an app; using MCP is optional.

Expose the smallest useful tool surface: searching approved manuals, reading one record or preparing a draft can be separate from sending a message or changing equipment. Keep authorization checks in the code or service that performs the action. Include a deadline, cancellation behavior and an observable result in the tool contract. These are proposed implementation choices; see [Tools, Skills & Integrations](/agents/tools-skills-protocols/) for the broader design.

## Route for the complete task

For a dedicated technical study of routing, decomposition, advice, token
cooperation and their evidence, see
[Local and Cloud Model Collaboration](/edge-ai/local-cloud-collaboration/).
This page keeps the focus on retrieval, state and action boundaries.

A hybrid system may choose local inference for a supported offline task and remote inference for a permitted task needing additional capability. RouteLLM studies learned selection between stronger and weaker models using preference data. Its routing overhead was measured on cloud VMs, and its authors identify application distribution shift as a limitation. It does not establish a universally reliable device router.[^routing]

A practical edge routing policy must also account for connectivity, device load, permitted disclosure and the remaining deadline. Our proposed policy uses explicit failure signals such as a retrieval miss, unsupported modality, exceeded context, or failed output validation. A model saying “I am confident” is not sufficient evidence to execute a consequential action. Calibrate any learned uncertainty threshold on the actual workload and include an abstention path.

Compare the whole path. A local request may wait for model loading, retrieval, prefill and decoding. A remote request may wait for upload, network exchange, server queueing and generation. A cascade that tries local generation before cloud generation can pay for both. These are components to measure, not a claim that either route is always faster. Use [Evaluation and profiling](/edge-ai/evaluation-profiling/) to define the comparison.

## A worked offline manual assistant

Consider a hypothetical tablet assistant for a user’s own appliance manuals. It can answer a question from saved evidence and prepare a note. It cannot control the appliance or contact a service provider. No system measurements are claimed.

| Situation | Proposed behavior | State to preserve |
| --- | --- | --- |
| Relevant passage is available locally | Quote the short needed passage and explain it | Manual version and page location |
| Exact model number is missing | Ask for the model number or a fresh image | Unresolved identity |
| Local model cannot produce a valid answer | Offer a permitted cloud request or show the source directly | Validation failure and selected evidence |
| Network is unavailable | Keep local search and source viewing usable | Draft and pending request |
| Remote request times out | Distinguish an unknown outcome from a confirmed failure | Request identity and observed status |
| User cancels | Stop new work and preserve the draft | Completed effects and remaining uncertainty |

This table is our proposed product behavior. If sending the note were added later, its permission and retry semantics would need a new review. A cloud fallback must not quietly send the whole document library merely because the local model failed.

## On device is not automatically private or secure

Local inference can keep model input processing on the device while the application still syncs files, calls online tools or sends telemetry. ML Kit’s terms make this distinction concrete: input and output processing stays local, but APIs can contact Google for updates and send performance and utilization metrics.[^privacy]

Our proposed data review follows the full route: captured input, document text, embeddings, prompts, tool arguments, outputs, logs and backups. Assign access and retention separately to each. An embedding store deserves review alongside its source text; a smaller representation is not a privacy guarantee. Restrict network destinations and credentials independently of model instructions.
