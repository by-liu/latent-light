A local model does not have to replace a powerful cloud model to be useful.
It can handle routine requests, supply specialized evidence, carry out focused
subtasks or ask for help only when needed. This page explains how those forms
of cooperation work, where they help, and what a convincing evaluation requires.

**The opportunity is a better complete system, not automatically a better answer.**
Apple discloses a product architecture spanning device and server models;
research explores much tighter cooperation. Neither establishes that a hybrid
system always beats a strong cloud baseline.[^apple][^minions]

[Figure 1](#figure-1) gives the central mental model: divide the work, but keep
the data boundary and the authority to act explicit.

Three distinctions make the rest easier to read:

- **Placement is not capability.** A local model may be a domain specialist;
  a cloud model need not be better on every input.
- **Cooperation is not one algorithm.** Choosing a model, exchanging advice,
  drafting tokens and splitting layers change different parts of the system.
- **Less cloud use is not less total work.** Count device computation,
  communication, checking and failures as well as the API bill.

These are the organizing distinctions used here, not a universal taxonomy.
This is the overview of **Local & Cloud AI**. For the focused architecture
where the cloud agent stays in charge and local models provide perception,
grounding or generation, read
[Cloud Agents & Local Specialists](/local-cloud-ai/cloud-agents-local-specialists/).
For applications to glasses, phones and cameras, see
[Smart Devices & Cloud Agents](/local-cloud-ai/smart-devices-cloud-agents/).

For the surrounding agent and permission boundaries, see
[Agents and hybrid systems](/edge-ai/agents-hybrid-systems/).

## What actually cooperates?

The following comparison synthesizes the cited mechanisms. The unit of work
is often more informative than the label “hybrid AI.”

<FocusCanvas size="wide" label="Compare local and cloud cooperation mechanisms">
<ComparisonTable id="collaboration-patterns" title="Seven ways to divide the work" label="Cooperation mechanisms, boundaries and tradeoffs" itemLabel="patterns" search>

| Mechanism | Unit and exchange | Best reason to investigate it | Main constraint |
| --- | --- | --- | --- |
| Request routing | Choose one model before generating | Avoid expensive inference on supported routine requests | Predict relative benefit on the actual workload.[^routing] |
| Answer cascade | Generate locally, check, then escalate if necessary | Inspect a real candidate before paying for more capability | Escalated requests pay for the earlier attempt too.[^frugal] |
| Task decomposition | Exchange instructions and subtask results | Process substantial local context through focused jobs | Coordination, evidence loss and sequential rounds.[^minions] |
| Advisory cooperation | Exchange tailored advice or a targeted question | Add domain adaptation or resolve a specific reasoning bottleneck | Train the communication policy; account for its overhead.[^advisor][^ask] |
| Collaborative decoding | Choose which model generates a token or span | Combine complementary model expertise during generation | Tight inference integration and error propagation.[^collm] |
| Speculative decoding | Draft locally; verify with the cloud target | Accelerate target generation without changing its intended distribution | Acceptance rate, verification access and network scheduling.[^speculative][^specedge] |
| Split inference | Send activations between parts of one network | Fit or schedule a model across hardware boundaries | Activation traffic, repeated synchronization and privacy exposure.[^neurosurgeon][^actinv] |

</ComparisonTable>
</FocusCanvas>

These can be combined. A router might keep simple requests local and select
a cooperative workflow for harder ones. That composition needs its own
evaluation; results for the individual parts do not establish the whole.

## Better than which baseline?

**Against local only**, a stronger remote model can supply reasoning or
knowledge the local model lacks. **Against cloud only**, the goal is often
similar task quality with less cloud expenditure, better availability or
less data movement. **Higher accuracy than either model alone** is a different
claim: complementary expertise and learned coordination can help, as studied
in Co-LLM, but arbitrary model mixing can also hurt.[^collm]

A fair quality claim must state what the cloud baseline received. Giving the
hybrid system better retrieval, more evidence, additional samples or domain
training can be useful engineering, but it does not isolate a gain from
placing computation on the device. Compare both the product and the mechanism.
The [evaluation plan](#how-to-evaluate-the-complete-system) below separates them.

## Choose before answering, or check an answer first

RouteLLM learns a query conditioned prediction of whether a stronger model
will win, using preference data. Its threshold trades strong model usage for
quality. This is a relative model selection problem, not a universal detector
of difficult questions.[^routing]

A cascade such as FrugalGPT instead examines generated answers and decides
whether another model is needed. The extra observation can improve the
decision, but requires paying for the first generation.[^frugal]

For a device deployment, our proposed policy first removes infeasible routes:
no network, prohibited disclosure, unsupported modality or a deadline the
route cannot meet. It then chooses among local inference, remote inference,
a bounded collaboration or abstention. A useful design objective is:

<MathExpression display number="1" tex="\begin{aligned}
a^*(x,s)&=\underset{a\in\mathcal A_{\mathrm{allowed}}(x,s)}{\arg\max}\;U(a\mid x,s)\\
U(a\mid x,s)&=\widehat Q-\lambda_C\widehat C-\lambda_T\widehat T-\lambda_E\widehat E
\end{aligned}" />

Here <MathExpression tex="x" /> is the request, <MathExpression tex="s" />
includes device and network state, and <MathExpression tex="a" /> is a route
or workflow. <MathExpression tex="U" /> is utility; every estimated quantity
on its right is conditioned on that route, request and state. Those quantities
are task quality, total cost, elapsed
time and device energy. The nonnegative weights convert those quantities to
a common utility scale. Disclosure permission belongs in the allowed set,
not merely in a soft penalty. [Equation (1)](#equation-1) is our design formulation,
informed by budgeted inference, not RouteLLM’s published objective.[^routing][^frugal]

Useful routing signals include retrieval coverage, input type, schema
validation and measured historical success for the model pair. A sentence
such as “I am confident” is not a calibrated probability. Keep threshold
selection separate from final testing, and recheck it after a model or
workload change. RouteLLM’s own overhead experiments used cloud VMs, not
phones, and its authors identify application distribution shift as a limit.[^routing]

## Turn a large task into local work

MinionS has the cloud model prepare focused jobs over short context chunks,
the local model execute them in parallel, and the cloud aggregate selected
results or request another round. Unlike unconstrained model chat, this
deliberately simplifies local work.[^minions]

[Figure 2](#figure-2) shows the original protocol comparison. Its generated
job preparation code is a research mechanism, not permission to execute
untrusted cloud code in an application.

The results have an important boundary: cloud token savings exclude local
hardware and energy, while the published latency experiment can be slower
than cloud only. See the [evidence snapshot](#what-the-measurements-establish).

For implementation, prefer an allowlisted task interface with fixed resource
limits over arbitrary generated programs. Track which source chunks each
result covers. A filtered result can contain an omission or a mistaken
extraction; aggregation does not independently restore missing evidence.
This is our proposed safeguard, not a demonstrated property of the protocol.

## Advice can flow in either direction

**A small model can help a strong one.** Advisor Models trains an open model
with reinforcement learning, using GRPO, to produce input specific advice for a frozen
black box model. The downstream outcome supplies the reward. [Figure 3](#figure-3)
separates that training loop from the inference path.[^advisor]

The paper reports gains on specialized tasks, but no significant improvement
in its MATH-500 limit study. It establishes an adaptation mechanism, not
measured phone efficiency. Frozen weights also do not guarantee that every
new advice prompt preserves output quality.[^advisor]

**A local model can instead ask a stronger one for help.** The October 2026
preprint *Learning to Ask* trains whether to consult, how to construct a
focused query, and how to use the answer. Its reasoning model and separate
Qmaker are both based on Qwen2.5-7B. Crucially, the evaluated design allows
at most one advisor interaction per trajectory; its budget experiments are
not a demonstrated general multi-round device agent.[^ask]

Conductor explores another direction: a trained 7B model chooses worker
instructions and communication structure. It is evidence about learned
orchestration, not proof that the conductor was benchmarked on a handset.
Its reported benchmark leadership is a dated paper result, not a current
universal ranking.[^conductor]

## Token cooperation is two different ideas

Co-LLM learns when a base model should defer token generation to an assistant.
The goal is to combine expertise and change generation quality. Its learned
deferral threshold needs task tuning; an assistant mistake can disrupt later
generation. Using a fine cooperation unit can also introduce a demanding
network synchronization problem when models are separated physically.[^collm]

**Exact speculative decoding has a different goal:** a cheap model proposes
tokens and the target verifies them with the appropriate acceptance and
correction procedure. Under the algorithm’s assumptions, the output has the
target distribution. That is not a guarantee that the target is correct, and
a cloud critique of a local answer is not this verification procedure.[^speculative]

SpecEdge places drafting on edge GPUs and verification on the server. It
overlaps drafting with verification and schedules multiple requests to keep
the server busy. This needs control of the serving path, not just a generic
chat endpoint. Its evaluated edge resources are consumer GPUs from edge
providers, which must not be confused with battery powered phones.[^specedge]

For the local inference mechanics, see
[Efficient inference](/edge-ai/efficient-inference/).

## Splitting a network is not splitting a task

Neurosurgeon predates current LLMs: its 2017 system chooses a layer boundary
between mobile and cloud computation across studied neural networks.
It sends an intermediate representation, not a subtask instruction to an
independent model.[^neurosurgeon]

In an autoregressive split, repeated activation exchange can become the
bottleneck. As an illustrative storage calculation, one tensor with 2,048
positions, width 4,096 and two bytes per value occupies **16 MiB**. Sending
that tensor over a 20 Mbit/s uplink takes about **6.71 seconds** for payload
alone. This is a hypothetical dense tensor, not a measured or necessary
handoff size; it excludes protocol overhead, compression and computation.

Fewer raw pixels or tokens leaving the device does not establish privacy.
ActInv studies reconstruction from split LLM activations under a passive
server threat model with full model knowledge. Its findings challenge the
assumption that hidden states inherently conceal the prompt; they do not
establish the same attack success against every split or protected service.[^actinv]

The two Minions percentages answer different questions: relative task
performance is not absolute accuracy, and cloud expenditure is not system
cost. Likewise, server throughput, generation step count, answer correctness
and user waiting time are not interchangeable metrics.

## Is this a real deployment direction?

**Yes, with different maturity levels.** Apple’s June 2026 foundation model
disclosure, updated September 9, describes two device models and three server
models, with Cloud Pro assigned demanding reasoning and tool use. This
supports a concrete hybrid product architecture, not an independently
measured share of traffic using each route.[^apple]

The original 2025 Gemini Robotics report specifies a cloud VLA backbone and
a local action decoder. Google’s separate June 2025 On-Device announcement
describes a model operating without a data network. These are distinct,
dated designs, not interchangeable claims that all robotics uses cloud
planning or that every newer release has the same boundary.[^robotics][^robotics-local]

Hazy Research’s May 2026 retrospective describes collaboration and routing
patterns in OpenJarvis. It is a useful first-party ecosystem signal, not
independent evidence of market-wide adoption or general performance.[^ecosystem]

The practical conclusion is narrower than “everything will be hybrid”:
**the design space is established; the best partition remains workload specific.**

## Make the handoff an evidence contract

A local component can contribute something more useful than a shorter
paragraph: a source passage, a table with units, a chart crop, an observed
event or a domain constraint. Our proposed handoff retains:

- Source identity, version, page or timestamp, and exact region when relevant.
- Observations separately from model interpretations and unresolved alternatives.
- Units, relationships and missing values, rather than only a fluent summary.
- Permitted use, disclosure scope and a way to request additional evidence.

For a VLM system, compare text summaries, structured extraction, selected
image crops and original multimodal input. A caption may lose tiny labels,
spatial relations or negative evidence. Treat the representation as an
experimental choice, not a free compression step. The information bottleneck
also appears explicitly in *Learning to Ask*’s limitations.[^ask]

Private source processing does not make derived messages private: names,
preferences and document facts may survive in a summary. Apple’s PCC is an
explicit security architecture; “we only send embeddings” is not an
equivalent guarantee.[^pcc][^actinv]

## A worked document assistant design

Consider a hypothetical assistant answering questions across a user’s
documents, tables and figures. The following is a proposed design, not a
measured deployment.

Local parsing and retrieval preserve original evidence. A local specialist
can answer supported routine questions; a permitted cloud path reasons over
selected evidence or asks for a specific missing crop. Neither route may
silently send the whole collection. [Figure 4](#figure-4) separates evidence
preparation from bounded assistance and validation.

For “How did the margin change?”, the local handoff might retain both period
labels, numerator and denominator, units, table locations and a conflicting
footnote. The cloud contributes interpretation; deterministic code checks
the arithmetic. If a graph label is unreadable, request that crop rather
than turn a local guess into a cloud fact. This example claims no measured gain.

Related application hypotheses include a camera that escalates selected
ambiguous events, a wearable that asks for help interpreting a user selected
scene, or a robot with an independently specified local control and safety
path. Each requires its own data, deadline and failure analysis. A model’s
proposed explanation is not a safety controller.

## Account for the complete critical path

A cascade can improve mean latency while making escalated requests slower.
Under a simple serial model with constant local time
<MathExpression tex="t_L" />, checking time <MathExpression tex="t_V" />,
escalation fraction <MathExpression tex="p" />, and complete cloud time
<MathExpression tex="t_C" />:

<MathExpression display number="2" tex="\mathbb E[T_{\mathrm{cascade}}]=t_L+t_V+p\,t_C" />

[Equation (2)](#equation-2) is our elementary accounting model, not a measured speedup.
With 0.35 seconds locally, 0.05 seconds checking, a 1.2 second cloud path and
20% escalation, the mean is **0.64 seconds**. But an escalated request takes
**1.60 seconds**, longer than cloud only. These hypothetical values omit
variance, loading, contention, caching and parallel work.

For a serial cooperative route, a more explicit approximation is:

<MathExpression display number="3" tex="\begin{aligned}T_{\mathrm{serial}}\approx{}&T_{\mathrm{load}}+T_L+T_C+T_V\\&+\sum_{r=1}^{R}\mathrm{RTT}_r+\frac{B_{\uparrow}}{U}+\frac{B_{\downarrow}}{D}\end{aligned}" />

Here <MathExpression tex="T_C" /> includes remote queueing and computation,
not network transfer; RTT accounts for exchange latency excluding the payload
serialization terms. <MathExpression tex="B" /> is bytes transferred and
<MathExpression tex="U,D" /> are effective bytes per second. Separate payload
and RTT this way to avoid counting the same transfer twice. Real pipelines
can overlap these terms, as SpecEdge demonstrates, so measure their critical
path instead of blindly adding them.[^specedge]

Track cloud billing separately from device energy, network energy and hardware
cost. A smaller model processing many chunks or staying resident continuously
can consume more resources than an occasional cloud request. That is a
possibility to measure, not a universal energy claim. See
[Evaluation and profiling](/edge-ai/evaluation-profiling/) and
[On device computing](/edge-ai/on-device-computing/).

## How to evaluate the complete system

Our proposed evaluation begins with a fixed task distribution, data access
policy, device class and service target. Define “better” before choosing a
router. Use held-out data by user, source or time as appropriate, not just
random neighboring chunks from the same documents.

<FocusCanvas size="wide" label="Baselines for a credible cooperation experiment">
<ComparisonTable id="collaboration-baselines" title="What each baseline rules out" label="Evaluation baselines and the explanations they test" itemLabel="baselines">

| Baseline | What it tests | What must remain comparable |
| --- | --- | --- |
| Local only | Does assistance add useful capability? | Local model, tools, data and task scope |
| Cloud with original permitted evidence | Does cooperation beat the strongest practical single model path? | Information access, samples, reasoning budget and disclosure policy |
| Cloud with the same local retrieval or extraction | Is the gain just better evidence preparation? | Identical evidence artifacts and retrieval budget |
| Simple rules and random routing | Is learning worth the training and serving overhead? | Cloud usage or total cost budget |
| Learned routing or proposed cooperation | Does the actual deployed policy deliver the claimed benefit? | Thresholds selected before testing; full runtime accounting |
| Offline routing oracle | How much room remains in choosing one model per request? | Same candidate outputs; no deployable access to test labels |

</ComparisonTable>
</FocusCanvas>

An oracle over whole-request choices is only an upper bound for that choice
set, not all forms of cooperation. A workflow that exchanges new information
can exceed it without a paradox; the action space is different.[^ask]

Report task correctness or completion, evidence completeness, unsupported
claims, abstention and error severity. Then measure **p50/p95 complete task
latency**, first useful response, bytes, actual cloud expenditure, device
joules and peak/resident memory. For continuous workloads, add energy over
time and missed events. Do not compare a server’s token rate to an
application’s completed task time.

Stratify the results by input length, layout, language, ambiguity, device
temperature, cold start and network state. Include disconnects, deadline
expiry, model updates and contradictory evidence. Test disclosure violations
and the path that requests additional data. If using a model judge, audit
its decisions on a human checked subset. Keep held-out prompts and evaluation
labels out of router and collaborator training.

Finally, plot the **quality versus total cost frontier** at a fixed latency
target, and the **quality versus latency frontier** at a fixed budget. Include
uncertainty and training/maintenance costs where they affect the decision.
One attractive average can hide the domain or network slice that fails.

## When not to add another model

Prefer a simpler route when direct cloud inference already satisfies the
privacy, cost and response requirements; when the local intermediate loses
essential evidence; or when repeated communication exceeds the deadline.
Prefer local only when connectivity or disclosure constraints rule out the
remote path. Better retrieval or a deterministic tool may fix the actual
problem without a second generative model.

Training is another alternative. [Knowledge Distillation](/knowledge-distillation/)
can move some capability into the local model before deployment. That is
different from consulting the teacher during each request. A useful research
question is whether recurring cloud assistance can become reviewed training
data for a future local release, with held-out regression and privacy checks.
It is not permission for uncontrolled online self-training.

The strongest opportunities appear to be **learning what help is worth asking
for, preserving evidence across the boundary, and adapting the cooperation
granularity to the hardware and network**. This is our synthesis, not a
claim that one protocol is universally best. Start with a measurable domain,
one clear handoff and strong single model baselines before adding more rounds.
