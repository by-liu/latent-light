## TL;DR

- **What it is.** DeepInfer is an open offline inference engine for
  DeepSeek-V4.1-Flash. Its companion, **deepseek-recipe**, handles API conversion,
  prompt encoding and response parsing.[^release][^recipe]
- **Why it matters.** The model and execution stack work together: reuse global
  history, rebuild a short local tail, balance expert work, verify drafts
  selectively and overlap CPU bookkeeping with device execution. The advance
  is their coordination, not one faster kernel.[^deployment][^mtp][^worker]
- **What the evidence says.** The authors publish throughput/interactivity
  curves and estimate dynamic-verification changes from **−1.5% to +11.0%**
  versus fixed-five verification at different loads. Conditions matter:
  this is not a claim that DeepInfer beats every other engine.
  [Read the benchmark analysis](#how-impressive-are-the-results).[^deployment]
- **What you still need.** A complete serving platform. Production routing,
  persistent KV storage and service orchestration are not bundled with the
  released engine.[^release][^deployment]

**Release snapshot: October 20, 2026.** Documentation, source code and benchmark
methodology inspected. No checkpoint, kernel or performance experiment was run
for this study. The [official deployment Q&A](https://github.com/deepseek-ai/DeepInfer/blob/main/doc/inference_deployment_qa.md)
provides the broader system context and builds on the

## What the release includes

| Piece | Scope of the inspected release |
| --- | --- |
| **DeepInfer engine** | Offline inference for DeepSeek-V4.1-Flash; default examples target the **1017 checkpoint**. The engine contains local runtime cache machinery.[^release][^examples][^cache-engine] |
| **Hardware** | **NVIDIA SM100** and **Huawei Ascend 950**. This is not a declared compatibility list for Hopper, consumer GPUs or laptop NPUs.[^release] |
| **deepseek-recipe** | Rust libraries and Python bindings for multiple API formats, prompt/token conversion and output parsing. It does not supply model inference, tool execution or HTTP transport.[^recipe] |
| **Surrounding service** | Production KV storage/management, complete vision/prefill/decode disaggregation and replica load balancing are not delivered as a complete service.[^release][^deployment] |

“Not a complete KV cache system” does **not** mean the engine has no KV cache.
Its GPU cache implementation is present. The missing boundary is the broader
production storage and management system.[^cache-engine][^deployment]

DeepInfer also has a lineage: the repository credits vLLM as its original
foundation, with inspiration from SGLang and TensorRT-LLM. The release is
valuable systems engineering, not a claim that every ingredient was invented
here.[^release]

## Follow one request through the system

For a language model, **prefill** processes the prompt and prepares reusable
state; **decode** repeatedly extends the answer. With images, a **vision
encoder** first supplies visual representations. DeepSeek describes separate
services for these stages, allowing resources and latency targets to be
managed independently.[^deployment]

[Figure 2](#figure-2) is the authors' **full inference-system architecture**.
It includes components described in the deployment note that are not all
included in the public engine. Read it as a system map, not an installation
manifest.

The path is:

1. **Convert and encode.** Recipe turns an API request into the appropriate
   model conversation, prompt and token sequence.
2. **Reuse and route.** The surrounding service finds reusable prefix state
   and assigns remaining work to suitable instances.
3. **Encode images when needed.** Vision work supplies embeddings to prefill.
4. **Process the uncached prompt.** Prefill prepares the state required for
   generation.
5. **Generate and stream.** Decode extends the answer; Recipe incrementally
   converts output into the chosen response protocol.

The protocol and engine interfaces are released. The complete routing,
persistent storage and service operation shown here remain a separate
integration problem.[^recipe][^deployment]

## Why the execution model matters

### Different stages deserve different hardware groups

**Expert parallelism, or EP,** places different MoE experts across devices.
**Data parallelism, or DP,** distributes attention work across requests/ranks.
DeepSeek describes attention DP paired with expert parallelism: requests
remain distributed for attention, while expert computation exchanges tokens
within a larger group.[^deployment]

Its deployment Q&A recommends small prefill groups when memory permits,
typically **EP2 to EP8**, and much wider decode groups, **EP64 to EP128**.
Wider groups improve the opportunity to combine expert work across many
concurrent requests, but introduce communication, balancing and failure-domain
costs. The production description says it does not currently use TP or CP;
the public examples nevertheless expose CP configurations. **A supported
capability is not the same as a production choice.**[^deployment][^examples]

Expert placement also cannot remain static when some experts receive more
tokens. The released EPLB policy allocates redundant copies of busy logical
experts and distributes physical copies across ranks using recent workload
statistics. This changes placement, not the learned identity of the
experts.[^eplb]

The broader production service balances a different problem: requests with
different context lengths and concurrency. DeepSeek describes distinct
prefill, decode and vision load balancers. Do not confuse these service
components with expert balancing inside an engine.[^deployment]

### Preserve global history, rebuild a short local tail

DeepSeek-V4.1-Flash separates causal encoder and decoder work. Its decoder can
consume shared global history without replaying the entire prompt through all
decoder computation. **Sliding window attention, or SWA,** still needs recent
local state.[^deployment]

SWA bounded replay addresses that remaining work. Rather than reconstruct
every layer's local state from a long history, the deployment description
rebuilds a short tail with a truncated local attention boundary.
This is an **approximation**, not an exact identity to full historical
recomputation.[^deployment]

The distinction in [Figure 3](#figure-3) is important: **a short local replay
does not mean the model sees only a short prompt**. Global state still carries
longer history; the optimization changes how local decoder state is rebuilt.

There are also two different numbers. The deployment explanation uses a
**128-token SWA window**. The public compact-mode configuration retains
**140 tokens**, including implementation safety margin. The code checks that
the retained suffix covers the window **plus the maximum backtracking
allowance**. Do not replace 140 with 128 simply because the conceptual window
is 128.[^release][^replay]

The repository's mask/compact test compares two implementations of the
truncated policy. Passing it would establish their equivalence under the test,
not equivalence between bounded replay and exact full-history recovery.
We did not run those tests.[^replay-tests]

<summary>Where the surrounding service keeps state</summary>

The deployment Q&A distinguishes three working sets: live state in GPU memory,
SWA state retained in host memory, and paged global block KV on a dedicated 3FS
storage cluster. It describes different retention policies for agent and
chatbot traffic. These are production design disclosures, not a distributed
cache service supplied by this repository.[^deployment]

The transferable idea is to choose storage by reuse value and recovery cost.
It does not follow that copying the same retention duration or storage
capacity is appropriate for another workload.

### DSpark: spend verification where it pays

Speculative decoding proposes draft tokens and lets the target model verify
a prefix. Verifying every request at the same draft length can waste work
when later proposals are unlikely to survive.

DeepInfer's **DSpark confidence scheduling** estimates how likely draft
prefixes are to be accepted, combines that with a device performance curve,
and chooses a verification budget. The implementation turns per-token
confidence estimates into cumulative prefix estimates before allocating
verification work.[^mtp]

For request <MathExpression tex="i" />, let
<MathExpression tex="c_{i,t}" /> be the head's per-position acceptance estimate
of draft position <MathExpression tex="t" />. The prefix estimate is:

<MathExpression display number="1" tex="\widehat{p}_{i,j}=\prod_{t=1}^{j}c_{i,t}" />

This explains why a later token cannot be selected independently of the
prefix it depends on. These are predictions used by a scheduler, not
guarantees of acceptance or calibrated correctness.[^mtp]

The scheduler seeks useful accepted tokens per predicted execution time,
rather than the largest number of verified tokens. Under asynchronous
execution, the CPU first fixes a budget using lagged information; GPU work
then corrects per-request lengths using the available confidence data.
The dependency management is part of the optimization.[^mtp][^worker]

### Overlap bookkeeping with device execution

CPU scheduling, GPU forward computation, sampling and output processing all
belong to the token loop. If the CPU waits for each device result before
preparing the next batch, the device can sit idle.

The released worker defers a decode step's output processing so it can overlap
with a later forward pass. It tracks previous step state and corrects sequence
metadata instead of pretending future samples are already known.[^worker]

As [Figure 4](#figure-4) illustrates, “zero-overhead scheduling” names the goal
of hiding scheduling on the critical path. It does not mean the CPU does no
work, every synchronization disappears, or every workload benefits equally.

### Kernels and low precision complete the stack

The runtime connects specialized components rather than relying on a single
universal kernel.

| Component | Role in the stack |
| --- | --- |
| FlashMLA | Optimized attention kernels used by the attention backend.[^attention] |
| DeepGEMM | Low precision matrix multiplication and grouped expert computation.[^deepgemm] |
| DeepEP | Expert token dispatch/combine communication.[^deepep] |
| DeepSelect | Top-k kernels for sparse attention and sampling.[^deepselect] |
| TileLang and custom kernels | Express specialized operations, including scheduling metadata and masks.[^worker][^release] |

DeepSeek describes FP4 use for routed expert weights and parts of the KV state,
with different scaling formats. “FP4” is not a statement that every operation,
activation or cache entry uses four bits.[^deployment]

This is why a model's small active-parameter count is not a complete deployment
budget. Retained weights, attention state, expert replicas, communication and
temporary buffers still have to fit and move.

## How impressive are the results?

The strongest evidence is **specific**: published operating curves, one
variable-verification comparison and a documented deployment strategy.
It is not a controlled leaderboard against every serving framework.

### Prefill: throughput has a latency price

The original prefill curve uses **four SM100 devices**, a **131,072-token
context**, EP4/DP4 and **140-token decoder replay**. Point labels are the
prefill token budget per rank. Larger chunks increase throughput, but
also increase time per prefill step.[^release][^benchmark]

Read three details before quoting [Figure 6](#figure-6):

- The context is **131,072 tokens**. Draft length is **fixed at three**.
- The plot assumes **75% per-token acceptance**, giving the plotting factor
  **3.25 tokens per step**. This is the plotter's accounting assumption, not
  a measured universal acceptance rate.
- Labels are concurrent requests **per DP rank**. At DP64, a label of 64
  corresponds to 4,096 requests across ranks, not 64 requests in total.

For orientation, the EP64 point labelled 64 is around **250 tokens/s/user**
and **16,000 output tokens/s/GPU** under this accounting. These rounded values
are read from the source plot, not raw measurements or a promised API speed.

Let <MathExpression tex="s" /> be measured steps/s,
<MathExpression tex="n" /> draft length,
<MathExpression tex="a" /> the supplied average acceptance factor,
<MathExpression tex="r" /> requests per rank and
<MathExpression tex="C" /> context-parallel size. The plotter uses:

<MathExpression display number="2" tex="\begin{aligned}\tau&=1+na\\ v_{\mathrm{user}}&=s\tau\\ T_{\mathrm{GPU}}&=\frac{sr\tau}{C}\end{aligned}" />

This reproduces the script's convention, not a general theorem about
speculative decoding. The raw benchmark's fixed-length throughput initially
uses **full acceptance**. Do not mix that number with the adjusted curve or
apply the same multiplier again to a different variable-length measurement.
The plotter explicitly rejects that incompatible case.[^benchmark][^plotting]

### Variable verification helps at some loads, not all

The deployment Q&A reports the following **estimated throughput changes**
from benchmark data for dynamic verification versus fixed-five verification
with EP64/DP64. This is a separate experiment from the fixed-three curve above.

| --- | ---: |
| 16 | **−1.5%** |

The low-concurrency regression is part of the result. Confidence scheduling
has its own overhead and operating point; it is not a blanket speedup.
These are author-reported estimates, not our measurements.[^deployment]

### Production scale and quality need separate interpretation

DeepSeek reports **155 trillion tokens/day for one cluster** and **US\$38 of
revenue per GPU-hour at valley pricing**. The note does not provide the token
mix needed to interpret 155T as generated output throughput. Revenue is not
profit, hardware payback or a transferable business forecast.[^deployment]

The released evaluation harness separately reports reference Pass@1 results
of **99.9% on AIME 2026, 93.4% on GPQA Diamond and 42.6% on HLE-Full** under its
documented protocol. AIME uses 32 samples per task and GPQA uses eight to
estimate single-sample accuracy; these are not best-of-32 or best-of-eight
success rates. Use the documented scorers and require complete task coverage
when comparing runs. Treat these as deployment sanity checks, not proof of
identical outputs under every optimization.[^evaluation]

No benchmark here independently establishes a cross-engine speedup, equal
NVIDIA/Ascend performance or a measured reduction in energy per task.

## Recipe is more than a chat template

A correct model can still behave incorrectly behind a poorly implemented
interface. Recipe converts **Chat Completions, Responses and Messages**
requests into a common conversation representation, then applies the correct
model encoding. Output parsing reconstructs reasoning, visible text and tool
calls for the selected protocol.[^recipe]

### Preserve the difference between content and control

Recipe records the exact ranges of intentionally inserted special tokens.
Ordinary text is encoded without the added special-token vocabulary.
A user who types the spelling of a role token does not thereby create a real
role boundary. Ordinary regions can also be encoded in parallel and joined in
the original order.[^tokenizer]

On output, token-ID-aware parsing can distinguish actual control tokens from
the same spelling expressed as ordinary text. A plain text stream loses that
token-identity information. Use a matching tokenizer when processing token-ID
chunks, and do not assume the text-only example preserves that distinction.[^recipe-tokenizer]

This reduces a specific control-token injection risk. It does **not** solve
semantic prompt injection, authorize tool execution or establish that a
model's answer is true.

### Stream valid pieces without waiting for the whole answer

An emitted chunk can end inside a UTF-8 character, a delimiter or a tool
argument. Recipe's parser retains unfinished state and emits determined
content incrementally. Its implementation uses incremental delimiter matching;
it does not repeatedly parse the entire accumulated response.[^parser][^decoder]

The practical lesson is that fast generation and fast delivery are different
problems. A server that buffers all tool arguments before returning them can
erase some of the responsiveness gained by the inference engine.

### A schema needs an enforcing backend

Recipe can translate a requested format into an output constraint.
The inference backend still has to enforce it. DeepInfer separately compiles
grammars and masks illegal tokens while sampling.[^recipe][^grammar]

For an already initialized DeepInfer runtime, the inspected interface accepts
a constraint such as:

~~~python
from deepinfer.sampling_params import SamplingParams

params = SamplingParams(
    max_tokens=128,
    so_args={"schema_type": "regex", "schema": r"[A-Z]{2}-[0-9]{3}"},
)
~~~

This is a configuration fragment, not a complete inference program.
The public engine uses the names **regex, json and ebnf** here.
A valid format does not establish factual correctness, and a generation stopped
by a length limit may still be incomplete. Check termination and validate the
result.[^structured]

## Practical recipes

Choose an entry point that matches your hardware and purpose. The examples
below are adapted from the inspected release and have not been executed here.

### 1. Explore the protocol layer without model weights

In a separate Python environment, install the library with
`python3 -m pip install deepseek-recipe`, following the project's package
requirements. Then inspect a rendered prompt:

~~~python
from deepseek_recipe import (
    ChatCompletionRequest,
    ConversionOptions,
    DeepseekV41Encoding,
)

request = ChatCompletionRequest({
    "model": "DeepSeek-V4.1-Flash",
    "messages": [{"role": "user", "content": "Explain prefix caching."}],
})
converted = request.convert(ConversionOptions())
rendered = DeepseekV41Encoding().render_conversation(converted.conversation)
print(rendered.prompt)
~~~

**What this does:** converts and renders a conversation. It does not run a
model or produce an answer. For actual token IDs, attach the matching tokenizer;
do not feed the rendered string through an arbitrary tokenizer and discard its
special-token ranges.[^recipe][^recipe-tokenizer]

The repository also provides a visual encoding/decoding demo and mock API
servers. Their sample responses are **mock inference**, not evidence that an
LLM is running.[^mock-server]

### 2. Run the official offline path on compatible hardware

The engine requires Linux, GCC 13 or newer, Python 3.12, and CUDA 13 for the
declared NVIDIA platform or CANN 9.2 for Ascend. Confirm device memory,
interconnect and model compatibility before building. This is a large-model
systems stack, not a laptop quick start.[^release]

The following illustrates the NVIDIA path from a reviewed checkout. Replace
the model path with an **existing compatible local checkpoint directory**.

~~~bash
python3.12 -m venv .venv
. .venv/bin/activate
export DEEPINFER_ACCELERATOR=nvidia
./build.sh

python examples/offline_inference.py \
  --model_name /models/DeepSeek-V4.1-Flash-1017 \
  --ep 8 \
  --check_structured_output
~~~

The build script installs dependencies and builds the vendored operators.
The examples can otherwise download their default checkpoint automatically.
Using a real local directory makes the weight source explicit. Review the
checkpoint's code and terms before executing it; the example loader enables
`trust_remote_code`.[^build][^example-config]

Eight-device offline examples are not the same as the efficient production
unit recommended in the Q&A. The latter recommends wide decode groups and
roughly balanced prefill/decode capacity. Do not present that recommendation
as the engine's absolute minimum supported device count.[^examples][^deployment]

### 3. Measure a controlled operating curve

Start from the official sweep script rather than a screenshot of one peak.
For an already configured compatible allocation:

~~~bash
# Fixed-length accounting, matching the plotter's supported convention.
export DEEPINFER_ENABLE_MTP_VARLEN=0
bash examples/sweep/run_sweep.sh decode my-decode-128k 131072 3 0.75
~~~

The parallel scale comes from the job environment and visible devices, not
from this command's tag. Record those settings, checkpoint, CP size, expert
replicas, context, uncached suffix, precision and draft policy. The script
writes raw JSONL points; retain them with the plot.[^sweep][^benchmark]

Measure without the profiler, then collect traces separately to inspect
kernels. The benchmark documentation warns that profiling perturbs timings
and that its throughput deliberately excludes certain logging/flush intervals.
These are steady-state engine measurements, not an online SLA.[^benchmark]

### 4. Build the missing service boundary deliberately

Connecting Recipe to an engine is an integration project. In addition to
inference and tokenization, decide how to handle authentication, admission,
cancellation, queues, timeouts, storage, routing, observability and failures.

The sample FastAPI server has **no authentication**, uses mock inference by
default, and does not filter private image-fetch destinations by default.
Keep it on loopback for exploration. Before exposure, supply a real backend
and enforce network destination checks, including redirects, along with
request and resource limits.[^mock-server][^recipe-development]

The engine's grammar compiler also warns against an unlimited distinct-schema
cache. Format constraints are another resource budget, not free input.[^grammar]

## What to take away

DeepInfer is significant because **it exposes how a particular model and
inference system are made efficient together**. Reusable global state, short
local replay, wider expert batches, selective verification, overlapped
scheduling and protocol correctness each address a different source of waste.

For engineers operating compatible clusters, it is code and a design reference
to evaluate. For readers without that hardware, Recipe and the source traces
still offer useful lessons. For a general production deployment, compare
capabilities and complete service needs before replacing an established stack;
the release alone does not establish a universal winner.
