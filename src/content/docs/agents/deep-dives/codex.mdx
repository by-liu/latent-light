Codex is best studied as a **controllable coding workflow with several integration
surfaces**. An interactive client, a program using the SDK and a cloud task do
not assign every runtime responsibility to the same owner.[^sdk][^cloud]
The useful question is where the conversation, execution and review live.

This study uses current official documentation checked **October 11, 2026**.
It explains documented contracts and an original task scenario. It does not
claim a new benchmark or knowledge of private service internals.

App Server supports custom clients that need conversation history, streamed
events, authentication and approval interactions. The SDK is the documented
route for automating coding tasks. These are integration choices, not different
names for a base model.[^server][^sdk]

## Think in threads, turns and items

The App Server contract distinguishes a **thread** containing a conversation,
a **turn** containing work in response to user input, and **items** such as
messages, tool calls, commands and file changes. Initialization establishes a
connection; thread APIs start or resume work; turn APIs begin or steer it;
notifications report incremental progress and completion.[^server]

This event model matters when an application displays progress. “The request
was accepted,” “a command is running,” and “the task completed” are different
states. Our integration lesson is to preserve those distinctions rather than
reduce all activity to an animated chat message. A lost client connection also
needs reconciliation with recorded task state before the application retries.

The TypeScript SDK exposes local thread creation, continuation and resumption.
The Python SDK controls a local App Server over JSON-RPC and published builds
include a pinned runtime dependency. An explicit sandbox argument and an omitted
argument are not equivalent: the omitted value uses the runtime's configured
default. Check the documentation matching the SDK edition you deploy.[^sdk]

## Local work and cloud tasks have different lifecycles

Codex Cloud uses a prepared project environment and gives each task its own
workspace. Work can continue while the user's machine is asleep, and the
workflow exposes changed files and checks for review. Shared setup does not
mean two tasks share one mutable working tree.[^cloud]

That changes the handoff problem. Local work must coexist with the user's
current edits and processes. A cloud task must carry enough project setup,
access and review evidence to make the result understandable after asynchronous
execution. Neither setting removes the need to inspect the diff.

The **managed Agents API** is another ownership choice: OpenAI manages the Codex
harness and durable sessions while the application supplies its integrations
and chooses an environment. The Codex SDK, the OpenAI Agents SDK and this managed
API should not be collapsed into one product contract.[^managed] Use the
[broader ecosystem](/agents/ecosystem/) to compare these implementation layers.

## Guidance and skills select what the model sees

AGENTS.md discovery builds an instruction chain from global and project guidance.
Within each searched directory, override and fallback rules determine which
file contributes; nearer project guidance is later in the concatenated chain.
The documentation describes the chain's construction at run start. It is not a
promise that every instruction file anywhere in a repository loads immediately.[^guidance]

Skills use progressive disclosure: identifying information is available first,
and the full instructions load when the skill is selected. Supporting scripts
and references can make a procedure concrete. Installing a skill changes the
available instructions and resources; it does not change model weights or grant
new operating-system authority.[^skills]

The current subagent documentation describes explicit requests and applicable
project or skill instructions as ways to authorize delegation. A delegated
thread needs a scoped task, relevant evidence and an integration owner. Context
isolation can help an investigation without making conflicting edits safe.[^workers]

## Approval and containment answer different questions

Sandboxing bounds the resources an operation can reach. Approval handles a
particular requested action or boundary crossing. The documented CLI presets
include read-only, workspace-write and full-access execution; filesystem and
network behavior depends on the effective configuration. Client and operating
system support also matter.[^sandbox]

A sensible design review therefore checks both policy and observed execution.
“Run the tests” may be authorized, yet a test command can require network access
or write a cache elsewhere. Conversely, a command can fit within the sandbox
and still be the wrong way to solve the user's task. Containment is not an
outcome grader.

An application should distinguish a denied command from a failing regression
check. The first calls for an allowed alternative or new authority; the second
calls for another inspection of the implementation. A final summary should
identify what actually ran, not merely what a generated plan intended.

For cloud work, review the returned changes against the receiving repository's
current state. For local work, protect the user's existing edits throughout.
The same acceptance criteria can apply, even though setup and recovery differ.

## What to learn from Codex

The transferable design is **a task lifecycle that a client can inspect and
control**. Events, persistent threads and bounded execution give an application
more structure to work with; the application still needs a trustworthy task
specification, integration and final review. Compare this with
[OpenCode's HTTP server boundary](/agents/deep-dives/opencode/),
[Pi's in-process SDK and subprocess RPC](/agents/deep-dives/pi/) and
[Claude Code's workflow extensions](/agents/deep-dives/claude-code/).
