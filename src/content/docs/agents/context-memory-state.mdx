Three different questions hide behind “the agent remembers.” What information
is visible to the model now? What can the system retrieve later? What work
can it recover after an interruption? Context, memory and execution state
answer different parts of that problem.

## Separate the stores

| Layer | What it contains | What it does not guarantee |
| --- | --- | --- |
| Active context | Instructions, selected evidence, recent observations and tool definitions | Persistence beyond this interaction |
| Retrieved memory | Stored facts, preferences, procedures or earlier experiences | Truth, freshness or relevance to this task |
| Execution state | Current step, pending actions, approvals and checkpoints | That an external action can safely be repeated |
| Artifacts and environment | Files, generated outputs and changes in external services | That a transcript accurately reflects current reality |

This is a teaching taxonomy, not a required storage schema. MemGPT supplies
the useful distinction between active context and external memory. LangGraph
distinguishes thread-scoped checkpoints from a store usable across threads;
its documentation also distinguishes transient in-memory storage from
persistence that survives a process restart.[^memgpt][^persistence]

## Context is a selection problem

A larger window does not remove the need to select relevant information.
Compaction summarizes earlier interactions; retrieval brings selected evidence
back; persistent notes preserve decisions and unfinished work. Each method
can lose or introduce information, so important constraints need explicit
preservation rather than an assumption that the model still remembers them.[^context]

For the invoice-review example, keep the current question, supported
findings, unresolved currency mismatches and exact document locations. Store a long
source separately and retrieve the relevant passage when needed. Do not turn
a generated summary into the primary evidence for its own claims.

Anthropic's managed architecture separates the session history, harness and
execution sandbox. This lets the system preserve continuity without relying
on the same running container. That is one implementation, not a requirement
to buy a managed platform.[^managed]

## Recovery is not blind replay

Suppose the invoice agent submits a request to publish its reviewed report. The service accepts
it, but the response is lost. Repeating the request could publish twice.
Restoring a checkpoint alone cannot tell the agent whether the first request
committed.

A proposed recovery design records an operation identifier before the request,
uses an idempotency mechanism where the service supports it, and checks the
external result before retrying. Stripe's API illustrates an explicit
idempotency-key contract. That contract is service-specific, not a universal
property of agent tools.[^idempotency]

The same distinction applies to payments, emails and database updates.
A replayed model call may also choose a different action. Preserve enough
evidence to reconcile completed effects, not just enough text to restart
the conversation.

## Memory needs governance

As a proposed memory policy, retain provenance, scope, freshness and a way to
correct or delete stored information. Separate a user's preferences from
facts about a document and from uncertain model interpretations. Retrieve
only information the current user is allowed to access.

Persistent memory can carry an error or injected instruction into later
sessions. It therefore belongs inside the security review, not merely the
personalization feature list. See [Security & Control](/agents/security-control/).

## What to retain in a handoff

For work that crosses sessions, a compact handoff should explain the goal and
constraints, what was actually completed, where the evidence and artifacts
live, which effects remain pending and what the next safe step is. This is a
proposed engineering contract, not a claim that longer notes are always better.
